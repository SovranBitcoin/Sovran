## Findings

### [P1] [PLAUSIBLE] features/theme/screens/ThemePreviewScreen.tsx:113 — Theme draft discard is button-only; gesture dismissal resurrects abandoned edits

The core dismiss-parity defect shape. `discard()` runs only in `handleCancel`
(:113-117) and `commit()` only in `handleApply` (:119-123) — the app's only
call sites of either (`features/theme/lib/themeDraft.ts:176,188`). No unmount
cleanup, no `beforeRemove`, nothing in `app/(theme-flow)/_layout.tsx`. The
flow is a gesture-dismissible modal (`modalFlow` → iOS `presentation:'modal'`,
`gestureEnabled:true` at `app/_layout.tsx:364`; Android drag-dismissible).

- **Scenario:** open Theme preview → change a wallpaper/album (draft dirty) →
  swipe the modal down → reopen Theme preview. The mount guard
  `if (!draftActive) beginDraft(UNIT_IDS)` (:109-111) skips re-snapshotting
  because the abandoned draft is still active, so the edits the user threw
  away render as pending changes (stale unit wallpapers, dirty Apply/Cancel
  footer). The in-memory draft never expires and Background/Gallery keep
  mutating it.
- **Not intentional draft persistence:** Cancel+reopen gets a fresh snapshot
  while swipe+reopen resumes dirty state — a deliberate persistence design
  would re-hydrate consistently; `themeDraft.ts:2-4`'s own contract says only
  Apply commits and Cancel discards. The mount guard exists to share the draft
  across the flow's three routes (`themeDraft.ts:5-8`), not across dismissals.
- **Fix shape:** move `discard()` into flow-level teardown (unmount cleanup /
  `beforeRemove` on the flow layout), leaving Cancel to only `router.back()`;
  or `beginDraft` unconditionally on preview mount.

### [P1] [PLAUSIBLE] features/composer/ui/PostComposer.tsx:618 — Alt-text editor: RN Modal with autoFocus input, zero keyboard avoidance, and a backdrop tap that silently discards typed text

The screen-level `KeyboardAvoidingView` (:360) wraps the Modal element in JSX,
but RN Modal content hosts in a separate native window — it cannot help. The
centered card (`altBackdrop` `justifyContent:'center'`, styles :801-826) holds
an `autoFocus` multiline input (:631-641); refuter geometry puts the
Save/Cancel row at roughly the keyboard's top edge on an 852pt iPhone (card
bottom ~535 vs keyboard top ~516), worse on shorter devices and as the
multiline input grows. Meanwhile the backdrop `Pressable` (:623) and
`onRequestClose` (:622) both run `setAltEdit(null)` — discarding the typed
alt text with no confirmation.

- **Scenario:** user attaches an image, taps ALT, types a description → Save
  sits under/at the keyboard edge; the obvious escape (tap the dim backdrop)
  silently throws their text away. Return key inserts newlines, so there is
  no submit path.
- **Attenuation:** occlusion half is iOS-and-device-dependent (Android dialog
  windows typically IME-resize); the discard-trap half is unconditional.
- **Fix shape:** keyboard avoidance inside the Modal (or convert to the
  sanctioned sheet primitive with `BottomSheetTextInput`); make backdrop tap
  save-or-confirm rather than discard.

### [P1] [PLAUSIBLE] shared/ui/composed/ModalLayoutWrapper.tsx:93 — Scroll container + `BottomButtons` footer are keyboard-blind; ClaimUsername onboarding is the worst exemplar

Root cause is shared: `AnimatedScrollContainer` (:93-107) and the plain
ScrollView branch (:335-347) set no `keyboardShouldPersistTaps` (RN default
"never"), and `bottomContent` (:350) renders `BottomButtons`
(`shared/ui/composed/BottomButtons.tsx:163-169`, `position:absolute;bottom:0`)
with no `KeyboardStickyView`. `KeyboardProvider` is mounted at the root, but
only chat surfaces use keyboard-controller primitives — nothing in
Screen/ModalLayoutWrapper/BottomButtons does.

- **Scenario (ClaimUsernameScreen.tsx:155):** onboarding user lands with the
  keyboard already up (autoFocus), types a username → first tap on a
  `DomainOption` row (:621-631, inside the scroll view) is swallowed by
  keyboard dismissal (double-tap), and the Continue footer is behind the
  keyboard until then. Self-heals after the swallowed tap — an annoyance, not
  a dead end — but it's the first-run surface.
- **Fix shape:** `keyboardShouldPersistTaps="handled"` in the shared scroll
  containers (or as a `Screen` prop), and a keyboard-aware variant of
  `BottomButtons` for input screens.

### [P1] [PLAUSIBLE] features/mint/screens/MintAddScreen.tsx:806 — Mint search results need two taps while the search keyboard is up

Same class, different chain: the results render through
`shared/ui/composed/List.tsx` (thin FlashList seam, injects no keyboard
props); the header `GlassSearchBar` is `autoFocus` (:666-675) with no
`onSubmitEditing`/`returnKeyType` mitigation; the Add(n)/Cancel footer
(:754-777) is the same non-avoiding absolute `BottomButtons`.

- **Scenario:** user searches for a mint, taps a result row → first tap only
  dismisses the keyboard, the row doesn't toggle; user taps again or assumes
  it's broken.
- **Fix shape:** `keyboardShouldPersistTaps="handled"` on the results list
  (List.tsx passthrough prop).

### [P2] [PLAUSIBLE] features/settings/screens/SettingsNetworkScreen.tsx:154 — Add-relay form: plain ScrollView, no persistTaps, submit button below the input

`Screen scroll="custom"` is explicitly hands-off (Screen.tsx:52,179); nothing
injects keyboard handling. First tap on "Add relay" (:255) with the keyboard
up is swallowed; nothing scrolls the bottom-of-page form above the keyboard
(`contentInsetAdjustmentBehavior` doesn't handle keyboards).

- **Scenario:** user taps the relay URL input → keyboard covers input+button;
  after typing, the first tap on Add does nothing.
- **Attenuation (why P2):** `returnKeyType="done"` + `onSubmitEditing={handleAdd}`
  (:246-247) is a working happy-path submit; settings is a secondary surface.
  ~15 other scrollers in the repo set persistTaps deliberately — this absence
  reads as oversight, not design.
- **Fix shape:** persistTaps + `KeyboardAwareScrollView` (keyboard-controller)
  for this form.

### [P2] [PLAUSIBLE] features/mint/components/MintCurrencyTabs.tsx:85 — Scroll-linked collapse animates six layout props (incl. fontSize) per frame

`useAnimatedStyle` worklets interpolate `paddingHorizontal`,
`paddingVertical`, `width`, `height`, `fontSize`, and two `gap`s from
`scrollY` (:77-173, :240-252) with no transform-only fallback — the icon's
`scale` transform is *additive* to animated width/height (:104 comment), not
a replacement. `fontSize` interpolation forces text re-shaping per frame.

- **Scenario:** user scrolls a mint screen → per-frame Yoga relayout +
  text re-shaping of the tab strip during the collapse band.
- **Narrowed by refutation (why P2):** `Extrapolation.CLAMP` with
  `COLLAPSE_THRESHOLD=50` confines changing outputs to the first 50px of
  scroll (constant values diff-skip after that), and the strip's outer height
  is pinned (`MINT_CURRENCY_TABS_HEIGHT`) so relayout stays inside the small
  tab subtree (2–5 tabs). No runtime jank evidence.
- **Fix shape:** pre-measure expanded/collapsed layouts and interpolate
  transforms/opacity between two absolutely-positioned states; at minimum
  replace `fontSize` interpolation with `scale`.

## Refuted this run (dropped)

- **Timeline entrance replays full choreography per remount** (the
  `line_anim firstRun=true` runtime lead) — the heavy draw-in is explicitly
  mount-terminal: dots skip choreography via `startedDone`
  (LoadingIndicator.tsx:668-681), connector `fillHeight` mounts *at* target so
  the logged `withTiming` is a documented visual no-op (TimelineRow.tsx:86,
  100-104 — `firstRun` is the diagnostic marker for exactly this), settle
  timeout fires at 0ms. Only an intentional opacity-only staggered row fade
  replays (TimelineCard.tsx:105-108, timelineTheme.ts:71-75). The runtime
  evidence was diagnostics, not jank.
- **`LinearTransition` on every history row → recycle slides/morphs** —
  FlashList items are *sections*; rows are keyed children that unmount/remount
  on recycle (fresh mounts never fire `layout` transitions, no `entering`
  set). The linear collapse is documented intentional design with explicit
  recycle coordination (Transaction.tsx:179-185, Transactions.tsx:837-842,
  ghost-hold at :221-222).
- **Story progress 20Hz JS drive** — gated to the single active story
  (`timeUpdateEventInterval = isActive ? 0.05 : 0`), listener is two JSI reads
  + one sharedValue write, animated node is a childless fill in a 2.5px track;
  sub-pixel stall impact. Sanctioned expo-video pattern (no UI-thread progress
  source exists).
- **SendScreen search-collapse height animation** — children are top-anchored
  absolute layers merely *clipped* by the animated container
  (`layerFill` has no `bottom`, SendScreen.tsx:673-678); no subtree relayout.
  One-shot 300ms, heavily comment-documented design.
- **SwipeableRow width-per-frame re-centering** — track is
  `flex-start`-anchored with fixed margins (:137-152); width growth only
  extends the clip. `failOffsetY` cedes vertical motion, so it never competes
  with scroll. Documented intentional sizing (:98-99).
- **ThreadView double-tap trap** — taps never reach the FlashList while the
  reply input is focused: `ThreadReplyBar` renders a deliberate full-bleed
  dismiss backdrop (`focused ? <Pressable absoluteFill onPress={dismissKeyboard}
  accessibilityLabel="Dismiss reply input">`, ThreadReplyBar.tsx:485-492,
  design stated at :332). First-tap-dismisses is the design working.
- **Composer main-input autoFocus racing the fullScreenModal transition**
  (dropped pre-verification) — static-only, and the repo deliberately accepts
  keyboard-during-present elsewhere (MintAddScreen header search); the
  `Keyboard.addListener`→setState in the composer is discrete show/hide, not
  per-frame.
