# Testing coverage ledger (source-backed)

This is the coverage contract for Sovran's JSON-native test system. It maps the
executable payment contract in `wallet/docs/STATE_MACHINE.md`, adjacent app
integration seams, and the broader product surface to the cheapest credible test
layer. A green device run is not evidence for a row owned by Vitest or Jest, and a
green pure test is not evidence for rendered/native behavior.

The JS/JF/JP columns are intended ownership, not blanket execution claims. The
simulator lane requires explicit destructive-reset approval and a fresh owned
simulator per selected scenario. The funded lane has an approved fail-closed
runtime boundary and independently requires test-fund-loss acceptance; authored
scenario deferrals still short-circuit before side effects. Generic live and
physical execution remain disabled. JSON validation, planning, focused recovery
tests, and fake-driver orchestration provide no product proof.

The full-suite manifest must reference every authored `e2e/scenarios/*.json` file.
Unsupported work remains visible as `deferredReason`; it is never omitted or
silently treated as passing. `default.json` stays unfunded and safe.

For JF work, availability and evidence are separate. Selection needs both
`--i-approve-destructive-reset` and `--i-accept-test-fund-loss`, then an unlocked
current `~/.cocod` wallet through one pinned version-`0.0.16` binary. JSON may use
only typed semantic counterparty operations against declared exact assets.
The generated mnemonic crosses only authenticated random-token loopback IPC and
never console/Metro output; mnemonic/P2PK private material and resumable tokens
remain in mode-`0600` custody. Host `recovery.sweep` performs NUT-13
restore/send-all with no UI amount, and exact cocod before/after deltas must
reconcile. A global lock serializes funded runs, while stale custody must be
automatically resumed and re-audited before a dead lock can be cleared. These
contracts are implemented. Prepared app Cashu outflows retry only when wholly
`UNSPENT`, repair already-credited `SPENT` evidence idempotently, and retain
custody for `PENDING`, mixed, or partial/excess/negative balance-drift states;
only an exact full credit is attributable. Zero-credit `SPENT` value is terminal
only as explicitly accepted `spent-uncredited` loss. Raw screenshots use a
randomized `0700` scope and `0600` file, with pre/post AX safety geometry;
render-bound toast probes appear only after the real HeroUI components mount.

## Layer and status vocabulary

| Code | Layer            | Proves                                                                                                                                   |
| ---- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `WV` | wallet Vitest    | Parsers, legal transitions, state-machine effects, mint/unit/fee/proof math, rollback contracts, stale-generation behavior               |
| `AJ` | app Jest         | Stores, persisted schemas, route adapters, source/toast mapping, native payload parsing, deterministic component/accessibility contracts |
| `JS` | JSON simulator   | Intended owner for real navigation, sheets, keyboard/clipboard/deep-link boundaries, rendered UI, AX and screenshot evidence             |
| `JF` | JSON funded/live | Intended owner for controlled round-trips, balance conservation, terminal transaction truth, and reclaim/sweep                           |
| `JP` | JSON physical    | Intended owner for real NFC/BLE/NutDrop radio transport and two-device timing                                                            |

Statuses used below:

- `covered` — the cited Jest/Vitest test is present and owns this contract.
- `offline-ready` — JSON validates and plans; fake execution may exercise the
  harness, but no real product result has been recorded.
- `authored` — JSON steps exist, but the named scenario has not completed the
  required product run; no execution is claimed.
- `product-run` — the named simulator scenario passed on an owned ephemeral
  simulator; evidence applies only to that exact scenario and run.
- `deferred:<reason>` — intentionally short-circuits without touching a device.
- `gap` — intended product contract is not shipped; keep a red/contract test at
  the cheapest layer and do not author expected-success device automation.

## Legacy `.sov` parity and retirement truth

JSON is the sole new functional/device authoring format. The old `.sov` source
corpus is no longer an execution dependency. Its useful behaviors informed the
four original payment definitions and the complete deferred plans in the current
inventory, but none establishes full parity and full `.sov` parity is not an
acceptance criterion for this slice. The explicitly legacy-derived cases are:

- Cashu receive dismiss: `receive.cashu.dismiss`.
- Cashu pending/cancel/reclaim: `send.cashu.pending-reclaim`.
- Lightning preview dismiss: `send.lightning.dismiss`.
- Copy/share/emoji/status/QR/cancel action matrix: `send.token.actions`.

The runtime under `app/codereview/log-doctor/test-dsl/` remains only because
log-doctor still imports it. It is not a second approved authoring format. Remove
that dependency in a separate log-doctor refactor after its non-test consumers
are decoupled.

## Coverage gates

1. Every `e2e/scenarios/*.json` file is referenced exactly once by `full.json`.
2. Suite ref id, file, lane, requirements, and end state match scenario metadata.
   The validator compares each ref with the scenario's effective requirements,
   including nested fixtures; cleanup is authored in scenario `finally` steps.
3. `default.json` contains only safe, unfunded, non-live scenarios.
4. `deferredReason` short-circuits before setup and emits a visible deferred result.
5. Every section 5 and section 11 row above has an owning test layer or an explicit gap.
6. A JSON scenario is promoted from deferred only after its selectors, fixture,
   assertions, and final-state plan exist. Simulator execution additionally
   needs destructive-reset approval and fresh per-scenario ephemeral-device
   ownership that cannot erase or reuse an existing simulator. Funded promotion
   additionally needs fund-loss acceptance, declared exact assets, pinned/unlocked
   current cocod, typed operations, mode-`0600` custody, a clean global lock/audit,
   host NUT-13 sweep, and exact final accounting. Live/physical promotion remains
   outside this approved boundary.
7. After authoring or changing JSON, re-open the named source and cited pure tests,
   validate, and dry-run. `onboarding.fresh` has simulator product evidence;
   `send.cashu.sat`, `receive.lightning.sat`, `receive.cashu.paste`,
   `receive.cashu.dismiss`, `toast.receive-lightning`,
   `send.cashu.pending-reclaim`, `send.token.actions`, `send.lightning.sat`,
   `send.lightning.dismiss`, `payment.request.delivery-rollback`, and
   `tx.source.cashu-paste` have funded simulator product evidence. No
   generic-live or physical scenario has passed.
8. The aggregate verification report runs wallet Vitest, app Jest, JSON validation,
   and offline harness checks separately; it must not imply that one runner
   covered another layer or that fake execution proves product behavior.
