id: F141
title: "Create Ecash takes 1.0 s online and 2.5 s offline from Next to the token; a second of it is screens recomputing"
priority: medium
needs: investigation
---

Measured on an iPhone dev build on 2026-10-12, sending 4 sat as ecash from proofs that match exactly, so nothing
is asked of the mint in either case:

| | Next pressed | prepared | execute starts | executed | token page |
| --- | --- | --- | --- | --- | --- |
| Online | 0 | about 290 ms | | about 1.0 s | 1.2 s |
| Airplane Mode | 0 | 460 ms | 1.48 s | 2.0 s | 2.5 s |

Read in the session log: between `operations.executeOfflineSend.prepared` and
`coco.manager.SendOperationService.executing_exact_match_send` the send does nothing for about a second while the
JavaScript thread is busy. `proofs:reserved` makes `walletContextTracker` refresh, and the amount screen, which is
about to be left, recomputes what every one of 17 mints can do (`screenActions.availability.*`,
`mintCapabilities.buildCandidates`, hundreds of `url.mint.normalize_key`) and reloads the balance breakdown.
Offline it is longer, by an amount not explained. Inferred, not shown: that this work is what delays the execute
step, and that it is the same work in both cases. A development build exaggerates it; no release build was timed.

Left because it is a measurement from one run on one phone and the cause is not confirmed, and because the
candidates (not recomputing availability on a screen that has handed off, or running execute before the refresh)
are choices in the payment flow.

## Done when

The gap between prepare and execute is explained with a profile or timed logs from a release build, and either the
work is moved out of the way so that an exact send shows its token in well under a second, or this entry records
why it cannot be.
