title: "Payment-request transport choice ignores the payee's preference order (NUT-18)"
priority: medium
needs: decision
---

NUT-18 says a payment request's `t` array is sorted by preference, but transport choice ignores the order. `wallet/src/operations/defaultOperations.ts:1759-1760` does `find(t => t.type === 'nostr')` and `find(t => t.type === 'post')` independently, then `:1782` takes Nostr only when there is no HTTP transport — so a payee listing `[nostr, post]`, i.e. preferring Nostr, is paid over HTTP. `machine/transitions.ts:150` picks the same way. The cause is an implementation constraint, not a decision: the comment at :1790 notes coco's `PaymentRequestsApi` has no Nostr support, so HTTP is the path that already works. Flagged by `nut18/transport-shape-and-preference` (0.78, 0.72, 0.70).

**Tried and reverted on 2026-10-12.** Walking the list in order (commit 69d7bfb45) was correct as routing, and a
Codex audit showed it made a payment less safe, because the Nostr branch of `executePaymentRequest` is weaker
than the HTTP one it would take over from:

- It builds the token itself and sends it by direct message. If the message fails after a P2PK-locked token was
  made, the proofs cannot be reclaimed (Coco 2.0.0 refuses to reclaim a pending locked send), so they stay
  pending and locked to the recipient. The app always supplies the direct-message callback, so "a callback
  exists" does not mean a message can be sent.
- It does not check the mint against the request's list or the amount against the request's amount at the money
  boundary; Coco's `paymentRequests.prepare`, used for HTTP, does. The payment machine checks both earlier, so
  this is a gap for a caller that bypasses it.
- `app/features/send/lib/sendDelivery.ts` tells the person the payment goes "to the requester's server" whenever
  a POST transport exists, and would have to follow the same choice.

**Done on 2026-10-12:** the Nostr branch now makes the two refusals at the money boundary that Coco's API makes
for HTTP: a mint the request does not list (unless the list is advisory) and an amount other than a valid amount
the request asks for (`wallet/src/operations/defaultOperations.ts`, `executePaymentRequest`; tests in
`wallet/__tests__/unit/default-operations.test.ts`).

**Left, in order:** make a failed Nostr delivery leave nothing stranded (the question below), make the preview ask
the same function which transport will be used, and only then honour the payee's order.

**Question for the owner.** A request offers both Nostr and HTTP and prefers Nostr, and it asks for ecash locked
to the payee. The app makes the locked ecash and then the Nostr message cannot be sent. Coco 2.0.0 cannot take
locked ecash back. What should happen?

1. **Keep it and keep trying (recommended).** The payment shows as "Waiting to deliver" and the app sends the
   message again in the background until it goes; the person can also send it again by hand. Nothing is lost, and
   the payee's preference is honoured. It needs a small saved list of undelivered payments (new saved data, added
   with defaults, nothing renamed).
2. **Wait for Coco.** Keep paying such requests over HTTP, as today, until Coco's payment-request API can deliver
   by Nostr and undo the payment itself. The payee's stated preference stays ignored until then, and this entry
   becomes `upstream`.
3. **Honour the order only for unlocked requests.** A request that asks for locked ecash and offers HTTP is always
   paid over HTTP; an unlocked one follows the payee's order, because unlocked ecash can be taken back when the
   message fails.

## Done when

The Nostr branch validates the mint and amount as the HTTP branch does and cannot strand locked proofs when
delivery fails; the preview names the transport that will be used; selection walks `info.transports` in order and
takes the first supported entry; a request offering only one transport behaves as today; covered by a unit test over both orderings
