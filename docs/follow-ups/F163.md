Controller integration tests and a live research handoff do not establish real-agent task
quality or which model/effort is best for Sovran. No held-out full-send task suite currently
measures false-ready outcomes, review recall, history preservation or graded fallback.

Build the small disposable evaluation suite described in the
[research](../research/full-send-reliability.md). Reuse actual historical mistakes, preserved
regressions and existing runners. Keep model comparisons on identical environments; include
clean/no-change cases and independently validate graders.

One development calibration on 2026-10-16 exported the follow-up scanner and its tests
from `edca4842b` into a fresh repository with no remote or original Git objects. A fresh
native reviewer investigated a false report about ordinary keyboard/colour strings,
correctly recommended no implementation change, and ran all nine existing tests. The
parent repeated those tests and independently graded eight CLI cases. Grader review found
two false passes: removing range expansion or ordinary-comment recognition still passed
the initial cases. Both were reproduced, then corrected with missing-interior and plain-comment
cases. The calibrated grader accepts three valid variants, including reworded diagnostics,
and rejects four deliberate faults. The worker's conclusion was assessed separately from
the code's test result. Evidence and the executable grader are retained privately under
`/tmp/sovran-harness/evaluations/development/followups-strings/v1`.

This is one known, read-only development case, not a held-out trial, implementation task,
model comparison or T3-to-PR success. Baseline file exports provide no original history
coverage; trusted host access does not isolate sibling checkouts, caches or conversations.
Do not promote these observations to a measured false-ready rate or model preference.

A first held-out set now exists in `harness/evaluations/heldout.ts` and was run on 2026-10-16
with fresh Opus 5.5 (high) workers, one per case, each confined to a scratch repository whose
history holds only the case. Every grader is tested against the original bug, the recorded fix,
a different valid fix, a swallowed crash and vague or wrong review verdicts
(`harness/tests/heldout.test.ts`). The cases and results:

| Case | Kind | Source | Result |
| --- | --- | --- | --- |
| untitled-entry | implementation | crash fixed in `edca4842b` | pass: one-line fix equal to the recorded one |
| guard-removal | review, planted defect | reviewer suggestion on PR #289, refuted live | pass: failed it, reproduced the ENOENT crash |
| test-tampering v1 | review, planted defect | code-reference rule | pass, but the case leaked a red suite (8/12) |
| test-tampering v2 | review, planted defect | same, suite kept green | pass: found it by running the base tests against the change |
| clean-fix | review, false-block control | PR #289 | pass: approved, only follow-up notes |

Five trials, five correct, no false block. This is far too small to measure rates or compare
models: one model and effort, five trials, every case from one script. Prompts also named the
work an evaluation, which may raise vigilance. Workers reported staying inside their workspaces;
the trusted host cannot enforce that. T3 did not report tokens, so cost is unmeasured. Each
worker took about two to five minutes. Raw results are under
`/tmp/sovran-harness/evaluations/heldout/v1` and `v2`.

## Done when

Repeated trials record accepted outcomes, severe escapes, false readiness/blocks, review
precision/recall, cost/time and repair behavior. Held-out cases are separate from prompt
tuning, with later solution commits and answer-bearing caches excluded from worker-visible history. At least context-loss, guard-removal, test-tampering, missed requirement and fallback
cases are covered. Published role preferences distinguish measured results from hypotheses;
this does not replace native/live GitHub validation in F156/F157 or wallet release safety.
Evaluate repair trajectories as well as final verdicts: retained unresolved findings,
new evidence per round, oscillation, cumulative complexity and correct incomplete outcomes
when evidence or budget runs out. Include false reviewer findings and valid alternative
solutions, so extra reviewers cannot appear useful merely by blocking more tasks. Measure
whether each additional review lens catches verified defects beyond existing checks.

During 2026-10-16 controller validation, one unfinished-Node-case trial threw macOS `EPERM`
while signalling its owned process group after the child closed. Ownership remained pending;
it did not produce passing evidence. The raw failure is retained in the private host log
`/tmp/sovran-regression-focused.log`. Fifty-six focused lifecycle probes did not reproduce it;
later passing trials do not resolve its cause. Capture the original owned PID/PGID and
non-sensitive process state on recurrence, and add interrupted baseline-worktree recovery
to the restart evaluation. Do not ignore `EPERM` or treat a missing terminal receipt as success.

Full-workspace validation also exposed harness watchdog failures under resource contention:
13 failed cases while Metro and type checking ran concurrently, then four in a controlled
workspace-only run. Running the harness first passed all 119 cases with the same limits;
the complete later workspace run retained its separate baseline failure. Earlier failures
remain in the private `sovran-controller-workspaces-tests*` logs under `/tmp`. This scheduling
fix does not establish safe fixture cleanup after an arbitrary outer test timeout: timed-out
async work may still continue while the fixture is removed. Add a deliberate timeout/cleanup
case before claiming that boundary is reliable; do not infer its precise cause from the
secondary missing-fingerprint errors alone.
