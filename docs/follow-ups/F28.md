title: "Bitchat native calls pass private keys positionally; native events are not validated"
priority: medium
needs: device
---

The bitchat JS-to-native interface passes five adjacent strings, two of them private keys, positionally (`startBLE`, `sendBLEPrivateMessage`), and native event payloads are typed but not validated at runtime. Move to Expo `Record` arguments in Kotlin, Swift and TS together; Metro, TypeScript and Jest now resolve the owned module source; bridge changes still require native rebuilds.

**Done on 2026-10-12, without a native build.** App code no longer passes look-alike strings to the module:
`startBLE` and `sendBLEPrivateMessage` take one request with named fields, and the positional native call sits in
one place beside the native interface (`app/modules/bitchat-module/src/BitChatModule.ts`). Every native event goes
through a reader in `src/nativeEvents.ts` before a listener sees it; a payload with a missing id, a field of the
wrong type or a body over 256 KB is dropped (`app/__tests__/bitchatNativeEvents.test.ts`). The readers were written
against what `BitChatBLEBridge` and `BitChatNostrBridge` send on both platforms.

**Left, and why it needs a build and two phones:** the bridge itself still takes seven positional arguments for
`startBLE` (two of them private keys) and four for `sendBLEPrivateMessage`. Moving them to Expo `Record` arguments
means changing `android/src/main/java/expo/modules/bitchat/BitChatModule.kt`, `ios/BitChatModule.swift` and the
`BitChatNativeModule` interface together, then a native rebuild on each platform. A mistake there compiles in
TypeScript and fails only on a phone, so it was not written blind. After the rebuild, run the Nut Drop and mesh
journeys on an iPhone and an Android phone, and check on each that a private message and a peer list still arrive
(a reader that is too strict would drop them silently).

## Done when

Record arguments on both platforms; malformed native events dropped by schema; Nut Drop and mesh journeys pass on devices
