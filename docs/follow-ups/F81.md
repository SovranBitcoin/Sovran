---
id: F81
title: "Release builds do not report Android storage pressure; two stores can still grow large"
priority: low
needs: decision
---

On Android, AsyncStorage is one SQLite database capped at 6 MB for every store together (`AsyncStorage_db_size_in_MB`, not overridden in this app), and a row over about 2 MB cannot be read back. The map cache (5.3 MB) now lives in a file, and on an existing Android install its old unreadable row was freed on first start (checked on the emulator); the app logs how full AsyncStorage is once per run (`storage.usage`, a warning near the cap or with an unreadable row), and logs a save that storage rejects (`store.<name>.save_failed`). Still open: the measurement only runs where logs are kept, so a release build does not report it; nothing is shown to the person when saves fail; `nostr-metadata-cache` and `own-content-store` can still grow large.

**Handed to the owner on 2026-10-12.** The app already logs how full AsyncStorage is once per run in a
development build. Three choices remain:

1. **Where does a release build show it?** Recommended: a line in Settings, Storage ("App data: 3.1 of 6 MB")
   that turns into a warning near the cap; the alternative is only in an exported support bundle.
2. **The two stores that can still grow large** are the same two as in the unreadable-copies entry (F72); decide
   them there.
3. **Raise Android's 6 MB cap?** It is a native build setting (`AsyncStorage_db_size_in_MB`). Recommended: not
   until the two stores above are bounded, because a higher cap only moves the cliff.

## Done when

A release build can report storage pressure (support bundle or a settings screen); the remaining large stores are bounded or moved to files; the cap is raised in the native build if still needed.
