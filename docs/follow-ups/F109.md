`app/__tests__/releaseFixtures/E20-0.1.4.ts` lists 40 stores under `defaultRows` and has 8 facts, against 98 in the
fixture before it, so it passing says little about the stores 0.1.4 adds. Its skeleton is written from the current
store registry, which the fixtures' own rule forbids. Three things would make the next release's fixture mechanical
and trustworthy:

- the completeness test rejects a non-cache store in the newest fixture's `defaultRows` unless a reason is given;
- a typed sample per store (so a new store does not compile without one) is written through the real persist and
  SecureStore code at release preparation and dumped as the fixture, with a fact per value;
- ~~a shipped fixture's stored data is pinned by hash~~ done on 2026-10-11: `releaseFixturesFrozen.test.ts` pins the
  stored data of every fixture but the newest (`releaseFixtures/frozen.ts`).

Left on 2026-10-11 because another session was editing the release fixtures and the completeness test.

fixture fails a test.
