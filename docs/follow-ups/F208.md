title: "A second rejected blob is overwritten when an older set-aside copy already exists"
priority: high
needs: decision
---

`app/shared/lib/persist/preserveUnreadable.ts` (about line 66) treats any existing `<store>:unreadable` copy as enough
to let the rejected main blob be overwritten. If a copy from an earlier rejection is still there and the main blob is
rejected again later with different contents, the newer contents are saved over and exist nowhere. For
`nut-drop-redeem-queue` that is ecash: a copy holding token X that this build cannot read, then a main queue holding
token Y that is rejected, loses Y. True of every store that uses the guard. Found by the Codex review of the redeem
queue fix and reproduced by it with an in-memory probe; not run in a Jest test here. Left because the repair writes
new keys or changes when saving is refused, which is a change to what is stored.

## Done when

A rejected blob is never overwritten unless those exact bytes are kept somewhere durable, with a test.
