title: "A store with one bad saved field runs on defaults for every field, and nothing says so"
priority: high
needs: decision
---

`createMergeWithSchema` in `app/shared/lib/persist/createMergeWithSchema.ts` runs one `safeParse` over the whole
saved blob and returns the store's defaults when it fails. Investigated on 2026-10-11:

- The saved bytes are no longer destroyed. `guardUnreadable` (`preserveUnreadable.ts`, wired in `persistConfig`)
  copies a rejected blob to `<store>:unreadable` before the store's next save. Nothing reads that copy back yet;
  that is F72.
- For the rest of the session the store still runs on defaults for every field, so one bad field in
  `settings-store` shows onboarding and terms again, and one bad field in `profile-store` shows no accounts. Keys
  and ecash are not in these stores and are not lost, but the app looks reset and the only trace is a
  `store.<name>.merge_rejected` log line.

What is left: when the whole blob fails and the schema is an object, parse each top-level field on its own, keep
the ones that parse and default the rest, still calling the guard's `reject` so the original bytes are copied
aside. A store whose fields depend on each other (`profile-store`: the account list and the active account) needs
to say so and stay all-or-nothing, or repair the dependent field. Then make a rejected identity store visible to
the person instead of looking like a new install.

**Mechanism done on 2026-10-11; which stores use it, and what a rejected identity store shows, are the owner's.**
`createMergeWithSchema` now reads a turned-down blob field by field for a store that sets `independentFields` in
`persistConfig`, keeps the fields that parse, and still has the original copied aside
(`createMergeWithSchema.test.ts`, `persistUnreadableGuard.test.ts`). `settings-store` sets it. No other store
does: whether a store's fields stand on their own has to be decided per store, and `profile-store` (the account
list and the active account) must stay all or nothing.

A field with `.catch` is a separate case, older than this: it degrades to its default while the blob as a whole
parses, so nothing is copied aside before the next save overwrites the value it could not read.

1. **Which other stores keep their readable fields?** Read each persisted store's schema; a store whose fields do
   not refer to each other can set `independentFields`. This part is a code change an agent can make, store by
   store, each with a test.
2. **What should a rejected `profile-store` show?** Today it shows onboarding, as if the phone were new, while the
   keys are still in the keychain.
   - **A (recommended). Stop on the startup-failed screen**, which already exists for a store that cannot be read
     (`loadRequiredStores`), and offer recovery from the phrase. Nobody creates a second wallet by accident.
   - **B. Rebuild the account list from the keys in the keychain** and carry on. No screen, but it guesses.
   - **C. Leave it.** The saved bytes are kept aside and a later release can restore them.

## Done when

A saved blob with one invalid field keeps its other fields after a restart, with a test per store class; a store
that declares dependent fields is not half-loaded; a rejected `profile-store` or `settings-store` is reported on
screen or in the startup failure path instead of showing onboarding.
