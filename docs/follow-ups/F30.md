Persisted fields hold Nostr seconds under millisecond-style names: `muteList.createdAt` (`feed-ignore-store`), `OwnProfileSnapshot`/history `createdAt`, `relayListStore.updatedAt`, `contactsUpdatedAt`, `EngagementRecord.updatedAt` (seconds beside sibling maps in ms), `WallpaperCatalogEntry.createdAt` (mirrored in `@sovranbitcoin/schemas`), and in-memory `RecentContact.timestamp`. Each now documents its unit. Rename only with a `version` bump, `migrate` and a regression test per store.

**Handed to the owner on 2026-10-12; no code changed.** Renaming a saved field is the one change this repository
does not let an agent make on its own: an install whose saved data no longer parses loses that whole store, and a
migration that is wrong does the same to everyone at once. Every field listed already says its unit in a comment,
so nothing reads it wrongly today. Which should it be?

- **A (recommended). Leave the saved names as they are and close this.** The units are documented where the fields
  are declared, and no rename means no migration that can go wrong.
- **B. Rename in memory only.** Keep the saved names, and map them to `…Sec` names when a store loads and back
  when it saves. Code reads clearly; saved data is untouched; each store gains a small mapping to maintain.
- **C. Rename on disk too**, one store per release, each with a version bump, a `migrate`, a fixture from the
  release before it and a test. Cleanest result, most risk, and `WallpaperCatalogEntry.createdAt` also has to
  change in `@sovranbitcoin/schemas`, which is another repository.

## Done when

Names carry `Sec`; an old blob still loads in a test for each store
