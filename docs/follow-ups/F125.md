`DM_RELAY_LIST_KIND` is only read: it appears in the read filter in `app/shared/lib/nostr/outbox/dmRelayDiscovery.ts`, and `serializeDmRelayList` in `app/shared/lib/nostr/outbox/nip17DmRelays.ts` has no caller outside tests. A client that follows NIP-17 looks up the recipient's kind 10050 list to know where to send, finds none for a Sovran user, and cannot start the conversation. Recorded in `docs/review/sweep-ledger.md` as an open gap and never given an entry; moved here on 2026-10-12.


**Looked at on 2026-10-12.** Publishing it is small: `useOwnRelayListSync.ts` already fetches the account's kind
10002 list and, when none exists anywhere, publishes the default relays once. The same place can do the same for
kind 10050 with `serializeDmRelayList`. What it publishes is the owner's call, because the list is public and says
where this person can be reached privately:

1. **Publish the default relays once, when the account has no kind 10050 list anywhere (recommended).** The same
   rule the app already follows for its public relay list: never overwrite a list that exists. Other NIP-17 apps
   can then message a Sovran user. The app must also read gift wraps from those relays, which it does today
   through nagg and the default relays.
2. **Publish only what the person chooses.** A "Message relays" list in Network settings, empty until they add
   one. Nothing is declared for them, and until they do, other apps still cannot message them.
3. **Do not publish.** Messaging stays between Sovran users, who find each other through nagg. This entry is
   closed as decided.

## Done when

The app publishes the account's kind 10050 list when its DM relays are set or change, alongside the relay list it already publishes, with a test that the event is built and sent.
