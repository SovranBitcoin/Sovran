The nearby-payment review ran all 576 app suites (5,561 passing assertions); the serial runner then stayed alive and reported Routstr SDK recovery imports after teardown. Earlier parallel runs also reported a worker failing to exit gracefully. This does not establish a clean shutdown or a baseline cause.

**One cause found and fixed on 2026-10-12; one worker still does not exit.** The imports after teardown came from
the Routstr recovery sweeps (`app/shared/lib/routstr/sdk/client.ts`). A test that simulates a paid request
failing starts one sweep at once and schedules four more, the last ten minutes later; the first ran on after the
test ended and imported the wallet adapter into a torn-down environment, and the timers kept the worker alive.
`settleRoutstrClient` now cancels the schedule and waits for running sweeps, and
`routstrChangeHeader.test.ts` and `routstr402BalanceSync.test.ts` call it after each test. A full parallel run
no longer reports an import after teardown. It still reports one worker force-exited, so there is a second
resource. A full run with `--detectOpenHandles` does not help: it runs in one process and Node crashes with a
segmentation fault after loading the experimental SQLite module. The next step is to bisect by folder with
workers on (`bun run test -- <half the test files>`) until the half that leaves a worker behind is one file. `vertexSigner.test.ts` and
`useWarmNip05Profiles.test.tsx` each failed once under full-suite load and pass alone.

## Done when

Identify the worker and resource responsible, fix its teardown at the owner, and complete the parallel full suite without the forced-exit warning
