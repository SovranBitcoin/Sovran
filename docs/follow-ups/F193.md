id: F193
title: "After a restart, a 0.1.3 payment to a re-encoded request waits until that request is shown again"
priority: medium
needs: decision
---

0.1.3 sends the whole encoded request it scanned as the payload's `id`. The receiver now swaps in the request's own id
when that string is byte-equal to one this wallet handed out for a request it holds
(`preparePayload` in `app/shared/lib/cashu/paymentRequestNostrTransport.ts`), and sets aside a wrap whose `id` is any
other valid request. Pinned in `app/__tests__/paymentRequestReleasedPayer.test.ts` against the real Coco.

What remains:

- The record of handed-out encodings (`recordHandedOut` in `wallet/src/payment-request-receive.ts`) lives for the app
  session only. Coco's stored `encodedRequest` always matches, but the receive hub, Nut Drop and the "as Ecash" screen
  show re-encodings (amountless, locked, fewer mints). After a restart, a 0.1.3 payment to one of those is claimed only
  once the wallet shows that request again; until then the sender's ecash stays in their pending send. The standing
  request is shown again whenever the receive hub or Nut Drop opens; an "as Ecash" request only when its screen is
  reopened. Fixing it means saving each handed-out encoding with its operation, which is new saved state.
- A payload Coco refuses before it records an attempt (an `id` naming no active request, a malformed payload) is still
  unwrapped and offered again on every poll. Telling a lasting refusal from a passing one needs a typed error from
  Coco, not its message text.

## Done when

A 0.1.3 payment to any request this wallet showed is claimed after a restart without reopening it, and a payload Coco
refuses for good is not offered again on every poll.
