---
id: F142
title: "Each app start adds two nearby standing payment requests and none is ever closed"
priority: high
needs: fix
---

Reproduced on an iPhone dev build on 2026-10-12, in four captures. `useNearbyDiscovery`
(`app/features/nearPay/hooks/useNearbyDiscovery.ts`) asks `ensureStandingPaymentRequest`
(`wallet/src/payment-request-receive.ts`) for the `nearby` request with the first five mints from
`rankAdvertisedMints`. That ranking puts funded mints first, and at launch it is computed once before balances have
loaded and again after. One recorded request is kept per unit and purpose, and a request with a purpose is reused
only when its mint list is the same, so every launch goes:

```
creq.standing.recorded_discarded  purpose="nearby" requestedUnit="sat" recordedUnit="sat" requestedMintCount=5 recordedMintCount=5
creq.standing.created             mintCount=5 encodedLength=507 hasP2pkLock=true
creq.standing.recorded_discarded  (same fields, 7 ms later)
creq.standing.created             mintCount=5 encodedLength=544 hasP2pkLock=true
creq.standing.reused              (twice)
```

The reason is logged as `unit_mismatch`, which is the fall-through label; the units match and the lists differ. The
same happens later in a session whenever the funded or trusted mints change (five or six discards in a two to four
minute walk). `createStanding` leaves the request it replaces active, so nothing is ever closed:
`cashu.creq.transport.poll_done activeOps=383` on this phone, and each launch activates all of them again
(`cashu.creq.transport.activated` 379 times in one burst). Memory of an earlier capture has the count at 17 in
September. Read in the source: the first resolve of a launch also takes 2 to 3 s (`creq.standing.resolve_timing`).

Came in with the nearby work in the 0.1.4 pull request: a purpose on the standing request (`3eb8fc418`) and
discovery warmed from the account provider at launch (`c58cfb39a`).

The owner decided on 2026-10-12: ask for the nearby request only once balances and trusted mints have loaded, and
treat a list that differs only in order as the same, so a launch reuses the recorded request. Requests that were
replaced stay active, so a payment sent to one is still claimed; the ones already accumulated are left as they
are. Not built in the session that found it, because it changes which request a payer is given.

## Done when

A launch with unchanged mints logs `creq.standing.reused` and no `creq.standing.created`, the count of active
requests on a phone does not grow from one day to the next, and the discard is logged with its real reason.
