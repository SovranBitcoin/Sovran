id: F174
title: "A Bluetooth token over the redeem queue's size limits empties the whole queue on the next launch"
priority: high
needs: decision
---

`useNutDropAutoRedeem` (`app/features/nearPay/hooks/useNutDropAutoRedeem.ts`) queues a token received over Bluetooth
without the limits the stored schema in `app/shared/stores/profile/nutDropRedeemQueueStore.ts` enforces (mint address
2048 characters, unit 16); the message path checks them in `dmEcashIntake.ts`. One over-limit entry makes the saved
queue fail to parse on the next launch, so it loads empty and every waiting token is left only in the `:unreadable`
copy, which nothing reads. A nearby peer can cause this. `app/__tests__/nutDropRedeemQueueOversize.test.tsx` pins it.
Left because it concerns saved data: the writer-side check changes what is saved, and a tolerant read schema is a
persisted-schema change. Run `persistence-release-safety` on whichever is chosen.

## Done when

An over-limit Bluetooth token is refused before it is saved, and a queue that already holds one still loads its other entries.
