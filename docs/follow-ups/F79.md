title: "No native scenario for StartupFailedScreen; the harness cannot make startup fail"
priority: low
needs: device
---

`StartupFailedScreen` (a failed migration, or a wallet that will not open) has test IDs (`storage-update-failed-screen`, `storage-update-retry`, `wallet-open-failed-screen`, `wallet-open-retry`) but no native scenario: the JSON harness has no way to make a startup migration fail. Checked by hand with a forced failure on the Android emulator (screen shown, Retry ran the migrations again, app opened) and on the iOS simulator (screen shown). The boot splash now fades as soon as a blocking stage fails instead of waiting eight seconds for the wallet screen's anchor; seen on iOS, not rechecked on Android.

**Not started on 2026-10-12: both halves need a simulator and an emulator.** The harness has no way to make a
startup migration fail, and a way to do it that has never been run on a device would be a guess. What is left:
add a debug-only launch argument that fails one named migration once, register the two screens as canonical
pages, author the smallest scenario that sees the failure screen, retries and reaches the wallet, and run it on
iPhone and Android. Until then both screens are listed in `app/e2e/schema/page-journey-gaps.ts` only if they are
canonical pages; today they are not pages at all.

## Done when

The harness can inject a storage failure at startup and a scenario covers both platforms.
