title: "Report coco's restore counter-0 bug upstream; cover wallets already left at 0"
status: open
priority: medium
needs: upstream

Coco's restore writes counter 0 after finding the signature at counter 0 (`lastCounterWithSignature ? … + 1 : 0`, coco-core `dist/index.js:3466`), so the next output for that keyset repeats one the mint has already signed. Worked around in the app's counter wrapper on 2026-10-10 (`app/shared/lib/cashu/cocoRepositories.ts`, `cashuCounterSafety.test.ts`): a restore's write of 0 is stored as 1, and a wallet an earlier build left at 0 is raised to 1, and saved, while it still holds a proof for that keyset. Still open: a wallet an earlier build left at 0 whose only proof for that keyset was already spent or in flight before this build ran is not detected; not reported upstream. Checked live against the public test mint on 2026-10-10: without the wrapper a restore left the counter at 0 and the next receive failed with `Duplicate outputs`; with it the counter was 1 and the receive succeeded.

## Done when

Reported upstream and fixed there, so the wrapper's workaround can go; the earlier-build case is covered by a re-restore or a check that sees spent proofs.
