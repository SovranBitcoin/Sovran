needs: decision

The redeem queue (`app/shared/stores/profile/nutDropRedeemQueueStore.ts`) persists whole bearer tokens through `createProfileScopedStorage`, which is plain AsyncStorage. That contradicts the secrets contract ([contracts](../review/contracts.md)). It predates message ecash (Nut Drop tokens were stored the same way), but message ecash widens it: a token parked for an untrusted mint stays there until the person reviews it. Move the queue's tokens into `createSecureVault` (`app/shared/lib/persist/secureVault.ts`), following `app/shared/lib/routstr/securePersistence.ts`: migrate the plaintext blob once, never replace a vault that has not been read, keep profile-switch rehydration and Delete All enumeration working, and batch writes so a status change does not rewrite every chunk.

**Handed to the owner on 2026-10-11; no code changed.** Reading the queue and the vault turned up a cost the entry
does not weigh, and it decides whether a payment can be lost:

- The queue saves a token the moment it arrives, before any network call, so a killed app cannot lose it. Tokens
  arrive over Bluetooth while the phone is locked and the app is in the background.
- `createSecureVault` stores 512 characters per keychain item and reads each back. A token may be 60,000
  characters (`NUT_DROP_QUEUE_LIMITS.token`), which is about 118 items for one token.
- The keychain can be unreadable while the phone is locked: `securePersistence.ts` already guards against iOS
  launching the app in the background with the keychain locked. A token that arrives then could not be saved at
  all.
- Mesh tokens are locked to this account's key, so a copied file cannot spend them. Tokens that arrive by direct
  message (`source: 'nostr'`) are plain bearer tokens.

Which should it be?

- **A (recommended). Move only direct-message tokens to the vault; keep mesh tokens where they are.** The tokens a
  thief could spend are protected, and a locked phone can still save a payment sent to it nearby. Needs one stored
  token per vault so a status change rewrites nothing, and a run on a locked iPhone and Android phone.
- **B. Move every token to the vault.** Nothing spendable or locked is left in plain storage, but a nearby payment
  that arrives while the phone is locked may fail to save, and saving a large token takes noticeably longer.
- **C. Leave the queue as it is and change the secrets contract to say why.** Mesh tokens are locked; accept the
  direct-message ones until they are redeemed, which is normally seconds.

## Done when

The redeem queue's tokens are held in a secure vault and no bearer token remains in AsyncStorage, including the blob written before the change. Tests cover the one-time migration, profile-switch rehydration, Delete All, and a status change that does not rewrite every chunk.
