# 0.1.4 release preparation

Draft preparation against `2d421e66`, checked 2026-09-28. Merging the version bump
to main starts production publication; this document is not approval to merge.

## Release inputs

The trigger is `app/app.json` → `expo.version`. Keep root `package.json`,
`app/package.json` and the app workspace entry in `bun.lock` aligned at 0.1.4.
Run `bun run assets:generate` and commit the version lockups, generated manifest
and brand gallery. EAS uses remote native build numbers with `autoIncrement`;
do not copy 0.1.3's iOS build 176 or Android version code 24. Keep the bootstrap
`baselineVersion` at 0.1.1.

## What 0.1.3 establishes

- [PR #259](https://github.com/SovranBitcoin/Sovran/pull/259) released source
  `d9ad12c4bde03b609cd90a4487c466b88007a4cb`, removing the unwanted activity
  recognition permission after 0.1.2 was withdrawn.
- The live [checkpoint](https://github.com/SovranBitcoin/Sovran/blob/release-state/active.json)
  is still 0.1.3 and has `complete: true`: App Store, Google Play, GitHub APK,
  Zapstore and Freedom Store each record version 0.1.3. These are recorded
  publication confirmations, not a fresh authenticated store-account audit.
- The checkpoint records manual first-production Play submission. The automated
  upload/production-track/commit path therefore still needs live confirmation on
  the next release. `app/eas.json`'s Android submit track is not that path:
  `release/android.mjs` publishes directly to Play production.
- Fixes from that release remain in main: expired Play edits (#260), Zapstore
  CDN readback (#262), large hosted files (#264), minimal formatted Freedom PRs
  (#265), and the correct Apple screenshot set (#266).
- Repository and `production-release` environment `RELEASE_ENABLED` both read
  `true`. The [recent successful run](https://github.com/SovranBitcoin/Sovran/actions/runs/36364283002)
  ran prepare and skipped every publishing stage because 0.1.3 was complete.

The controller archives the completed checkpoint and pins the next release's
source SHA. Hourly runs resume that source; later controller fixes can apply
without rebuilding different app code. Keep the checkpoint intact. The Android
lane can proceed while Apple waits, and website availability advances only for
confirmed channels. Store review and the external Freedom PR can still require
human action.

## Pre-merge blockers

1. `bun run knip` fails on existing main code: unused `network-timeouts`, seven
   exports in `app/shared/lib/routstr/curatedModels.ts`, and the `MintProbe` and
   `CuratedModels` exported types. Production validation runs Knip as a blocking
   gate. Resolve the findings and rerun before merging; do not raise budgets.
2. `bun run e2e:test` has 727 passing and 10 failing tests: coverage-ledger
   indexing, canonical scenario verification/Android AX contracts, and the
   fixture-expanded matrix/chunk-plan invariants. JSON validation passes, but
   the production workflow requires both checks.
3. `bun run check:react-compiler` finds two new bailouts in `MintAddScreen.tsx`
   (ref access during render) and `useColadaTransactionAnnotation.ts`
   (memoization could not be preserved). `bun run check:styling` also rejects
   new debt in `MintInfoScreen.tsx` and `Notice.tsx`. Both are production gates.
4. `bun run screenshots:status --strict` reports 0/212 baseline screenshots
   current, 76 blocked recipes, 15 missing captures and 207 outdated captures
   (categories overlap). The both-platform refresh plan was inspected. Several
   recipes require effect/privacy review or unsupported fixtures, so a blanket
   capture run cannot establish readiness. Complete reviewed capture work and
   regenerate the selected website outputs under the release runbook. The
   production controller does not currently enforce this whole-library gate;
   a version-only PR also does not trigger the path-filtered Website workflow.

## Verification boundary

Release/controller tests and archive tests exercise mocked provider failures;
they do not validate current signing credentials, agreements, store permissions
or a real EAS archive. This preparation does not submit builds, alter release
variables or checkpoints, or merge/publish anything. See the PR for the executed
validation results. New native device captures and store builds remain outstanding.
