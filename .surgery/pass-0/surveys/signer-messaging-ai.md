## 4. Obvious defects — source-path verified, not runtime reproduced

### D1 — BitChat non-BLE-DM send failure silently discards the message

**CONFIRMED by complete TypeScript caller path.** `app/features/bitchat/hooks/useBitChat.ts:414–419` catches a rejected native send, only logs and removes the optimistic row; the promise resolves normally. Applies to public BLE, public geohash and Nostr-DM branches at lines 430, 545 and 563. `app/features/bitchat/screens/GeohashChatScreen.tsx:300` returns `sendMessage(text)` to ChatScreen. `app/shared/ui/composed/chat/ChatScreen.tsx:278–285` clears the draft before dispatch and relies on the consumer to surface errors. No hook error field or failed row is returned, and the screen banners describe Bluetooth/reachability/moderation, not this send failure.

Trigger: open one of these chats and have `sendBLEMessage`, `sendGeohashMessage` or `sendGeohashPrivateMessage` reject. Result: draft empty, outgoing row disappears, no user-visible send error/retry. Expected: visible failure and retained/recoverable message or draft; a rejected send must not become an invisible completed action. A fix can remain runtime/UI-only; **no persisted shape, migration or wire-format change is required**. BLE-DM has a separate failed-message path and is not included in this finding.

### D2 — Whitenoise inbox startup storage failure has no handled exit/recovery

**CONFIRMED by complete TypeScript setup path.** `app/features/whitenoise/hooks/useWhitenoiseInbox.ts:60–105` invokes an async setup function with `void` and no catch. `cursorStore.getItem` at line 69 delegates directly to awaited AsyncStorage at `storage/asyncStorageBackend.ts:99`; I/O rejection propagates (only decoding errors are converted to null). Subscription is not constructed until line 81. Per-event catches at lines 91/137 cannot catch setup failure.

Trigger: AsyncStorage rejects reading `whitenoise:<account>:inbox-cursor:last-seen-at` during a mounted provider's initial setup, then recovers while hook dependencies stay unchanged. Result: unhandled rejected promise, no inbox subscription, no retry or exposed initialization error. Expected: handled initialization failure and an explicit recovery/error path. A fix can be runtime-only, **without changing stored keys, schema, migration or wire format**. Do not silently bypass the cursor with an empty read as the only recovery policy.

No other issue is promoted to an obvious defect. Concerns involving actual Marmot emission order, native delivery receipts, profile-remount guarantees, provider response reality or old-release migrations were not fully traced and are not findings.
