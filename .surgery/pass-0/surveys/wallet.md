### Storage, network and adapter ownership

No direct AsyncStorage/MMKV/SecureStore/SQLite/filesystem persistence calls were found in `wallet/src`; persistence is deliberately delegated. The package nevertheless defines durable shapes and identity keys:

- Annotation `quote:`/`op:`/`id:`/hashed `raw:` keys and serialized metadata fields (#30–31). App callers include its cashu annotation adapter and `app/shared/lib/migrations/dataMigrations.ts`. Key and codec changes can orphan prior records even without touching an app storage call.
- `ReusableQuoteIdentityStore.get/set/subscribe` (#28–29), backed by `app/features/receive/lib/standingQuoteIdentityStore.ts:15` → active profile `mintStore.standingQuotes`. The adapter dereferences the active store at call time. Unit helpers use memory stores, so app account switches during async writes are not covered by those tests.
- Legacy record schemas and `records.writeGroup/writeQuote` (#42) serialize claim progress; `LegacyClaimPorts` protects liveness after awaits. Old Redux bearer proof/quote JSON is input, not a format safe to tighten.
- Mesh queue status/attempt/backoff records (#41) are written through a live app port; Coco proof/operation/history persistence is invoked through Manager, not reimplemented in this package.
- `CashuSeedCache` (#59) is injected by the app. The package derives seed bytes; secure key/mnemonic persistence is outside it.

`safeFetch.ts:127` is the single direct `fetch` call found. LNURL callback parameters, NIP05 results, mint catalog/app-view reads, mempool HTTP and accelerator POST feed it. Spending and mint HTTP are behind Coco; DM transport is injected through `sendNostrDM`; clipboard/share/NFC/QR/chain adapters are injected via `wallet/src/adapters/types.ts`. Tests generally stub these external ports. QR/deep-link outputs and NUT-18/Cashu JSON are wire contracts even though the package owns no route files. No screen/route implementation lives under `wallet/src`.

## 4. Obvious defects (fully traced; no fixes made)

### D1 — reusable quote single-flight returns a different Manager's address

**CONFIRMED package-level behavior**, `wallet/src/quotes/reusable.ts:69,101–103,119`. Start `ensureReusableMintQuote(A, sameInput, storeA)` and leave its create pending. Call `ensureReusableMintQuote(B, sameInput, storeB)` before A completes. `sameInput` is identical mint URL/method/unit. The global `inFlight` key omits Manager identity, so B returns A's promise immediately. B never calls its Manager or writes its identity store. Its returned address/quote is A's. The per-Manager resolved cache at `:76` does not protect this early return.

In-memory reproduction with distinct fake Managers produced:

```json
{"managerBResult":{"quoteId":"A","request":"address-A"},"managerBCreateCalls":0,"managerBIdentityWrites":[]}
```

Expected: deduplicate within the owning Manager; B must resolve/create against B's wallet and B's identity store. This is observable through #26's receive address. App account cleanup calls `disposeReusableQuoteFlights` (`app/shared/lib/cashu/manager.ts:1932`), which mitigates a simple account-switch overlap; the reproduction establishes the exported package contract defect, not that a production profile switch currently reaches this exact interleaving. Cleanup only clears a map, it does not cancel its already-running tasks. Full app account-switch schedule was not exercised.

A fix can scope transient flights by Manager without changing a stored schema, migration or wire format. It must also preserve ensure/rotate coordination and avoid an old completion deleting a newer flight after cleanup. Existing `unit/reusable-quotes.test.ts` lacks the cross-manager test that the standing-request helper already has.

### D2 — history fallback selects an unrelated row before the exact identity

**CONFIRMED in both exported operation factories**, `wallet/src/operations/receiveOperations.ts:99–105` and `:521–528`. The purported exact-match preference is implemented inside a single `Array.find` predicate. An earlier row with the right type/mint but a different operation/quote passes the set-difference fallback before the iterator reaches the exact match. A failed before-snapshot makes every existing row eligible, too.

Concrete receive input/state: before page empty; receive executes `my-op`; direct canonical history lookup returns null (the code explicitly supports this fallback); next page is `[unrelated-row(other-op), correct-row(my-op)]` from the same mint. Actual returned finalized `historyEntry` is `unrelated-row`, operation `other-op`. Concrete mint variant: prepare `my-quote`; next page is `[unrelated-mint(other-quote), correct-mint(my-quote)]`; returned entry is `unrelated-mint` with `other-quote`. Both cases were run through the real exported factory with in-memory ports and returned the wrong row on the first poll.

Expected: search the whole page for exact identity first, and never adopt a row explicitly belonging to a different operation/quote merely because it appeared since the snapshot. This affects the entry passed to the machine's navigation/notifications and downstream transaction annotation/link callbacks; the mint path can return another quote's payment request. Execution itself already occurred: this defect is result attribution, not evidence of a duplicate spend.

A fix need not change stored data, migrations or wire formats; it changes which existing row is returned. The erroneous current result must not be preserved as a characterization QUIRK. Regression tests exposing D1/D2 will fail today's code and should be kept separate from pass-0 tests required to pass today.

No other defect is asserted. In particular, I did not label best-effort enrichment failure, timeout fallback, display-zero amounts, or cancelling uncertain operations as bugs without tracing the owning external implementation.
