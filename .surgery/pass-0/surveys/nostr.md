## Storage and wire footprint to preserve

- `nostr/` itself supplies memory caches, HTTP app-view bindings, Primal cache REQ/EOSE frames, and raw Nostr relay REQ/EVENT/CLOSE/CLOSED handling; no durable store was identified there. Envelope order/aggregates and missing IDs are part of callers' observable result, not incidental implementation.
- `A/secureStorage.ts:24` names `user_mnemonic`, `derived_keys_<index>`, `cashu_mnemonic_<index>`, `cashu_seed_<index>`, `imported_nsec_<pubkey>`, per-account and legacy migration markers, `secure_key_index`. It also consults legacy AsyncStorage (`reduxEraRoot.ts:16`: `persist:SOVRAN`) and reset/recovery manifests outside this area. Do not infer that key-list enumeration here exhausts manifests owned elsewhere.
- `giftWrapCache.ts:5` uses `nip17-unwrap-cache:v1` and `nip17-unwrap-cache-neg:v1`; `nip04Cache.ts:4` uses `nip04-cache:v1` and `nip04-cache-neg:v1`, via shared pubkey-scoped persistence. Unwrapped bodies/plaintext are sensitive persisted data.
- Relay list persists `entries/updatedAt/hasPublished/source` as `nostr-relay-list-store`; media server persists `server` as `nostr-media-server-store`, both through profile-scoped storage. Builder mirrors entity profiles through external `nostrMetadataCache` after 5 seconds and at teardown.
- Own sync/moderation/profile publish write stores owned outside this directory: social, own-content, owned-media, ignore list, profile and own-profile metadata. Those are observable writes even though persistence implementation is elsewhere.
- DM output includes kind1059 ciphertext, recipient/self wraps and event IDs; direct-message preparation is a persisted-retry-compatible signed-event/relays schema. NIP65 kind10002 and NIP17 kind10050 lists differ. Profile kind0, encrypted mute kind10000, report kind1984, Blossom authorization kind24242/imeta and zap request all have externally meaningful tags/content.
- No screen/route is defined inside this area. Screens above are consumers. No QR/NFC decoder was found here; `njump` produces share URLs/nostr URIs and memo helpers encode nprofiles. Wallet payment intents/QR parsing are outside this assignment.

## 4. Obvious defects

### D1 — CONFIRMED by isolated execution: cleared capability cache is repopulated by the old request

`nostr/src/capabilities.ts:50–57,67–69`. Start `serviceInfo()` against a deferred fake fetch; call `clear()`; resolve the original fetch with capability `old`; await it; call `supports('old')`. The old `.map()` still assigns `cached`; no new fetch occurs. Reproduction output: `{"calls":1,"afterClearSupportsOld":true}`. `clear()` should invalidate the earlier generation for subsequent lookups, while the original caller may still receive its original answer. A late old error can likewise clear a newer pending slot, though only the old-success scenario was executed.

Executed via `bun -e` importing the real transport and capability modules, using an injected deferred fetch and an in-memory Response. No network or storage. Existing `NT/transport` tests do not cover reset. No production caller of `.clear()` was established, so impact is confirmed at the exported API, not asserted as an observed UI outage. Fix is memory lifecycle only: no persisted data, migration or wire-format change needed.

### D2 — CONFIRMED by end-to-end source trace: own-profile sync ignores a winning equal-time event in a later batch

`app/shared/lib/nostr/ownsync/useOwnEventsSync.ts:101,135–137`. Batch one supplies kind0 event ID `b…`, timestamp T>0: profile is ingested and timestamp ref becomes T. Batch two supplies a different valid kind0 ID `a…` at the same T. Its ID is fresh, and `partitionOwnEvents.ts:104` selects it (using the package `supersedes` ordering, timestamp then lower ID). But the hook admits only `created_at > lastProfileCreatedAtSecRef`, so it never calls `applyProfile` for the replacement. `applyProfile` delegates to `ingestOwnProfileMetadata` after active-pubkey validation; that downstream function would accept the equal timestamp. The explicitly implemented ordering elsewhere (`profile/publishOwnProfileMetadata.ts:135–136`) also selects the lower ID at equal timestamps. Thus splitting the same events across batches changes the eventual cached profile.

Expected: retain both timestamp and event ID for newness and admit the winning equal-time event consistently with batch partitioning. This was source-traced, not run in React/native. Existing partition tests cannot catch the hook's extra timestamp-only gate. Fix touches decisions that write existing profile/cache fields; it need not change stored shape, migration or event wire format. Report only; no fix applied.

No other suspected lifecycle issues are promoted to defects. In particular, first-run NIP65 empty reads, the shared one-year filter on replaceable kinds, hanging self-copy publication and post-switch subscription batches require additional runtime/dependency evidence before calling them confirmed app failures.
