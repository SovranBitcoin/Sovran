## Scope and meaning of coverage

This is an inventory of **40 grouped observable boundaries**, not a count of exports or a certification of every path. Several exports share one lifecycle/wire contract and are deliberately grouped. **15 pinned, 16 partially pinned, 9 unpinned** at the grouped-contract level (table below). “Pinned” means relevant behavior assertions exist in inspected test source; it does **not** mean tests passed today. “Partial” means focused behavior coverage exists but important portions of the named boundary remain untested, or only helpers/source text are checked. “NONE” means no behavioral test found by import/name searches in app tests and colocated tests. Test paths below are relative to `app/__tests__/` unless prefixed otherwise. Native E2E scenarios were not executed or exhaustively mapped; see exclusions.

The app supplies adapters and presentation to `wallet` through `wallet/react`, `wallet/operations`, and the root `wallet` API. Coco owns proofs and canonical operations. This report covers those calls, not wallet package implementation. Read root AGENTS, architecture overview, contracts, jevgrep guidance, and TypeScript/type-system guidance. No payment policy was changed, so no sibling-wallet policy comparison was needed.

### Persistence and wire boundaries to preserve

- Manager naming is `coco.db` for account 0 and `coco-${accountIndex}.db` otherwise (`manager.ts:457,465`). Seed-cache calls use captured accountIndex and mnemonic hash (`manager.ts:832–867`); SecureStore implementation/keys live outside this area and were not audited.
- Nearby journal schema is version 1 with `outbound[operationId]` delivery and `inbound[sha256(payload)]` recovery records (`nearbyPayments.ts:31–69`). Exact JSON payload and prepared Nostr envelope are persisted before transport; do not reconstruct different bytes on retry. Trust, request membership, locked-to-me and DLEQ admission precede durable inbound insertion (`:113–145`). Rejected payloads are retained, not retried as new receives (`:224–231`).
- `standingQuoteIdentityStore` writes `mintStore.standingQuotes`; fixed request customization writes annotation key `op:${operationId}` (`ReceivePaymentRequestQuoteScreen.tsx:230–237`). Other config/bridge writes include scan history, location, distribution, counterparty and lock annotations. These stores are out-of-area owners; tests of rendering do not certify their persistence migrations.
- DM intake/legacy Nut Drop writes profile `nutDropRedeemQueueStore`; decrypted thread/conversation snapshots in `dmSnapshotCaches.ts` are **session-only, persist:false**. Last-message metadata is persisted separately; bearer DM content is not made durable by these snapshot caches.
- `paymentRequestNostrTransport` accepts giftwrap kind 1059, decrypts locally, defaults missing unit, forwards envelope id as `transportMessageId`; terminal finalized/rejected only are session-deduped. Outbound creq transports carry an nprofile and relay hints.
- Serialized history/entry route parameters are still external input. Route shells mostly validate string length/presence; deeper entry decoding belongs to `useScreenActions`, not these string schemas. No claim that these route schemas alone authenticate canonical history.
- NFC Type4 reads enforce NLEN and exact chunk lengths; writes zero NLEN, body, final NLEN. `buildTextNdef` includes NLEN, so the standalone writer's total-size check must retain that meaning. Cashu QR payloads and creq/BIP321 payloads have distinct animation behavior.

## 4. Obvious defects

**D1 — fixed-amount ecash receive can permanently display “waiting” after a completed receive (source-confirmed; no runtime reproduction).** `app/features/receive/screens/ReceivePaymentRequestQuoteScreen.tsx:83–139` initializes `prState='requested'` and only advances on future `receive-op:prepared`, `receive-op:rolled-back` or `receive-op:finalized` events. Trigger: the request is finalized before this component's effect subscribes (e.g. fast payer pays during navigation, or the same request display is mounted after completion). The full path is `sovranPaymentConfig.ts:1267–1274` → router replace with serialized request → `app/app/(receive-flow)/paymentRequest.tsx` direct export → schema parsing → state initialization → subscriptions; the screen never queries an existing operation/history status. `syntheticEntry` maps requested to executing/pending, and customization remains visible only because prState is still requested. With no later matching event the display has no path to settled status even though funds are already received. Expected: bootstrap from the canonical recorded receive attempt and reconcile events without a read/subscribe gap. Also reset state/rejection if entry.operationId changes while mounted; current local state is not keyed to that identity. **Fix need not change stored data, migration, or wire format**: read the existing canonical state and maintain an identity-bound UI snapshot. Do not modify request payload semantics to fix a display race. No existing screen boundary test found.

No other obvious defect is asserted. In particular, nearby retained rejection, unknown spent-probe queueing, default-unit compatibility, and dropped writes during profile barriers are intentional observed behaviors, not bugs. A later adversarial/runtime audit could find more; this survey does not certify their absence.
