# Non-Zustand persistence survey

Read-only source survey, 2026-11-10. Candidate **87b8afffee50316f65b36d8a3efa422898e1cbd3**, branch `surgery/pass-1`; released baseline **d9ad12c4b (v0.1.3)**; original map candidate **5651d4720**. `@H` below means the pinned candidate, not a moving HEAD; `@R` means d9ad12c4b; `@M` means 5651d4720. Paths are repo-relative. This report is the only intentional file write. No commits, checkout, stash, installation, native launch, or test execution.

**Conclusion: incomplete certification, with confirmed inventory omissions and stale test claims.** No changed derivation path or requested native storage dependency version was found between R and H. The important gaps are native BitChat persistence outside the inventory, opaque SDK recovery payloads without a content version, and test coverage that records some durable rows without invoking their readers. One confirmed released-value discontinuity is intentional: pending NIP46 pairing in plaintext is discarded on upgrade, not migrated. This costs the pending pairing, not the wallet key.

Used the supplied 584-line HEAD, 320-line release and 542-line map surface lists as discovery leads; compared their normalized differences and independently searched current sources. Old source was read only with `git show`. `jg "What persistent secrets databases and files exist outside Zustand stores?"` returned discovery incomplete, HTTP 402 (max concurrent requests: 32); continued with `rg` and source reads.

## Ranked findings

### 1. Native BitChat keys and preferences are missing from the map and from its automated inventory (confirmed; identity/privacy and contact data)

The map contains the JS `bitchat-dm-messages-store`, but no rows for native identity keys, peer summaries or vendor preferences. Both R and H install Noise and Ed25519 identity material in native persistence. iOS scopes keys as `sovran_<sha256(scope)>_<key>` and services as `<service>.sovran.<hash>` (`app/modules/bitchat-module/ios/ProfileScopedBitchatKeychain.swift:21@R`, identical at `:21@H`); bridge writes `noiseStaticKey` and `ed25519SigningKey` (`BitChatBLEBridge.swift:292@H`). Android scopes preference filenames similarly (`android/src/main/java/expo/modules/bitchat/ProfileScopedContext.kt:20@R` and `:20@H`) and writes `bitchat_identity` and `bitchat_crypto_secure` (`BitchatIdentityInstaller.kt:90@R`, unchanged at `:90@H`).

These are regenerable deterministic BLE keys, not newly discovered wallet seed authority. However, vendor favorites, fingerprints and seen-message caches are also routed through the wrapper; exact vendor inventory is **unknown** because both BitChatVendor submodule directories are empty in this checkout. It would be false to certify “every native durable thing” without them.

The scanner deliberately excludes `ios`, `android`, `vendor` and non-JS extensions (`app/__tests__/persistenceSurface.test.ts:25@H`); it also has no filesystem-write inventory. Passing that snapshot cannot detect a native key rename or a new file. `bitchatProfileScope.test.ts:34@H` checks JS scope selection; Android source tests check source strings; neither opens released preferences/keychain data. Fix to the record: enumerate native storage using pinned vendor revisions and add actual native upgrade fixtures, separate from the JS message store.

### 2. SDK recovery contents have no format version or runtime shape validation at the app boundary (confirmed structural gap; money recovery risk is inferred)

`app/shared/lib/routstr/sdk/driver.ts:16@H` identifies `api_keys`, `child_keys`, `xcashu_tokens`, `cached_receive_tokens`; `:45@H` reads JSON with no payload schema. The outer secure vault has version 1, SHA256 and committed slots, but those certify bytes, not SDK object meaning (`app/shared/lib/persist/secureVaultManifest.ts:6@H`, `secureVault.ts:25@H`). Nonsensitive SDK values likewise use bare JSON. The driver did not exist in R (new unreleased surface), but the map already lists it; do not call it missing. Since M the driver and secure persistence have gained write barriers/failure handling, while the vault byte format remains the same.

`routstrSecurePersistence.test.ts:136@H` pins captured ownership and `:149@H` pins voided write failures; `routstrSecureVault.test.ts:24@H` pins large-token round trip. No frozen release-fixture row exercising these SDK vault contents was found in `app/__tests__/releaseFixtures` (searched `routstr-sdk`, `xcashu_tokens`, `cached_receive_tokens`). There is no released SDK value to upgrade from 0.1.3; the gap is preserving this candidate's recovery material across the *next* SDK/content-shape change. No actual loss from an R-written value established.

### 3. Missing wallet file detection cannot identify loss on the first upgrade from 0.1.3 (confirmed limitation; money recovery visibility)

Names remain `coco.db` / `coco-<index>.db` (`app/shared/lib/cashu/manager.ts:143@R`, `:458@H`). Missing files are created empty by SQLite. H only prompts restore if the account row already has `walletDatabaseCreated:true`; every R row lacks it (`app/shared/lib/cashu/walletDatabaseRecord.ts:11@H`, `:40@H`; call before migration at `manager.ts:823@H`). Thus an R install whose database is absent still looks like a first open. This is not a newly introduced data deletion and cannot be repaired by guessing that every old empty wallet lost funds.

The map's wallet treatment should distinguish absent-on-first-upgrade from absent-after-recording. `walletDatabaseLost.test.ts:133@H` explicitly permits the first empty database, `:139@H` tests recorded loss. A release fixture listing database names is not a missing-file recovery test (`releaseFixtures/format.ts:52@H`).

### 4. Released pending pairing is deliberately abandoned; the map says it is read (confirmed, limited loss of one pairing attempt)

R writes `nip46-pending-pairing` in AsyncStorage (`app/features/nostrSigner/lib/pairingIntentStorage.ts:23,75,82@R`). H writes `nip46_pending_pairing` in SecureStore, never reads the legacy row and removes it on take/clear (`:31–34,85,92,169@H`). An unexpired R-written intent is therefore lost on the next take, even if perfectly valid. This is explicit security policy, not accidental schema rejection. The map row “same key read” is stale (same old behavior at M).

`nip46PairingIntentStorage.test.ts:229@H`, “is removed on the next take and never handed out,” pins the discontinuity. This is **not** an untested upgrade bug. The current secure intent has no content version, but is a short-lived strict schema with TTL; malformed/oversized input clears and reports none. Add the new key and intentional abandonment to the map.

### 5. NO TEST claims and fixture completeness overstate different things (confirmed; assurance gap)

- Coco's old “no database files” gap is stale: `app/__tests__/cocoDatabases/manifest.json:1@H` now lists eleven adapter versions (0.6.0, rc11, rc.30, rc.32, rc.34, rc.47, scoped rc.0, rc.5, 1.0.0, 1.0.1, 2.0.0). `cocoDatabaseUpgrade.test.ts:206,215,246,262,324,370,391,420@H` checks migration, proofs, balances, counters, operations, history/keyring, reopening and the app's backup/open path. This is real old SQLite-file coverage via Node SQLite, not native-platform certification.
- Whitenoise is no longer wholly untested: `whitenoiseStorage.test.ts:61,74,102,159,200,225@H` tests tagged version-1 bytes/bigints, read failures, history and cleanup. Still no released MLS group-state/key-package fixture read through the current Marmot implementation for every namespace. No Whitenoise durable rows found in release fixtures; a `whitenoiseEnabled:false` setting is not one.
- NPC/NIP04 rows exist in E18/E19 and the upgraded E20 disk (`E18-0.1.1.ts:762–767,796@H`; E19 kept list `:1585–1588@H`). Their preservation is pinned byte-for-byte, not by invoking NPC or decrypt-cache readers. NIP17 historical-reader coverage not found.
- Bunker secrets: unit cases exist, including malformed blobs (`nip46BunkerSecrets.test.ts:205,215@H`), but still no native released-keychain upgrade test or release fixture for the bunker array.
- Logs, native peer summaries, NDK cache contents, harness files and secure intent/vault rows still lack comprehensive released-reader fixtures. Wallpaper and file-cache fault tests exist; they do not certify historical native directory upgrades.
- `releasedPersistedSurface.test.ts:99@H` checks source strings for secure keys/database names; `persistenceSurface.test.ts:116@H` compares a current source snapshot. Neither asserts compatibility of arbitrary old non-store values. `releaseFixturesCompleteness` primarily drives completeness from persisted-store declarations, so unrepresented native/dynamic keys can stay green.

## Derivation comparison

`git diff d9ad12c4b HEAD -- app/shared/lib/nostr/keyDerivation.ts` shows only exporting `getRootSeed` and registering disposal that zeroes/clears its process cache. Derivation formulas and paths are unchanged: NIP06 `m/44'/1237'/i'/0/0`, Cashu derived branch `m/44'/129372'/0'/i'/0/0`, imported branch `m/44'/129372'/0'/mappedIndex'/1/0`; entropy-to-mnemonic then BIP39 seed remains the Cashu process. R/H evidence is the same path literals in `keyDerivation.ts`; no claim that E1's raw-child seed equals this later BIP39 seed.

Callers changed materially. `loadAccountKeys.ts:63–201@H` now reads stored data unchanged, chooses identity, verifies it independently, then writes caches. R's NostrKeysProvider contained the old cache-first loading. `manager.ts:761@H` checks staged credentials before opening a DB; recovery checks the phrase against existing derived rows. Existing mismatches can now stop startup rather than silently opening the wrong identity. `accountIntegrityBoundaries.test.ts`, `accountIntegrityStartup.test.tsx`, `secureStorageLifecycle.test.ts`, and release fixtures pin parts of this behavior; they were not run here. This is a deliberate stricter reader, not a changed derivation path. No well-formed healthy R cache shown to lose its identity in this survey.
