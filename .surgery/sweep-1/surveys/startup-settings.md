## Broken

1. **B1 — A pending theme Apply can save account A's draft into account B. `list` (high).** `app/features/theme/lib/themeDraft.ts:115,124,188-218`; `app/shared/lib/profile/inProcessProfileSwitch.ts:57-77`; `app/features/theme/screens/ThemePreviewScreen.tsx:114-131`. Start Apply on A with a primary wallpaper download pending, dismiss the editor, then complete an opt-in in-process switch to B before the download resolves. The switch replaces the session store with its initial state but does not increment the module-level `draftRevision`. Apply checks only that revision, then writes its captured A snapshot through the now-B `useThemeStore`. The write barrier is already open after the successful switch. **Verified at the store seam:** transpiled the actual themeDraft module in memory with store/download stand-ins, began Apply, performed the same initial-state replacement as the switch, changed the backing theme to B, then resolved the download. Apply returned `true`, wrote once, and replaced B's album, wallpaper and mode with A's. This did not run the native switch. **Failing test:** hold A's download, reset session stores and hydrate B, release the download; expect false and B unchanged. **Boundary:** saved profile theme values change; no wire-format change, existing wallpaper download involved. Owner decision: invalidate pending Apply at account teardown and bind the commit to its initiating account; include switch/persistence regression coverage. Distinct from F189: this reproduces with a successful download.

2. **B2 — Refresh turns an in-flight media deletion into a failure and offers Delete again. `list` (medium).** `app/features/settings/screens/SettingsMediaScreen.tsx:49-58,115-118,299-303`; `app/shared/stores/profile/ownedMediaStore.ts:152-166`; `app/shared/lib/nostr/media/deleteOwnedBlob.ts:50-67`. Confirm Delete, then Refresh while the server DELETE is outstanding. Refresh includes the `delete-requested` row; a HEAD result of true changes every non-`live` state to `delete-failed`. The screen stops saying “Deleting…” and makes the trash action available even though the original DELETE has not answered. An older HEAD can likewise overwrite a later successful deletion. **Verified reducer:** extracted and transpiled the actual `markChecked` property in memory; `delete-requested` + `exists=true` produced `delete-failed`. **Failing test:** defer DELETE, refresh with HEAD=true, assert the row remains pending and cannot be deleted again; also resolve a pre-delete HEAD after DELETE success. **Boundary:** persisted media ledger and admission of network DELETE requests. Owner decision: make status probes subordinate to deletion ownership/generation; do not infer a deletion outcome from a probe belonging to an earlier state.

3. **B3 — Continue can submit a username that the current input validation rejects. `list` (medium).** `app/features/onboarding/screens/ClaimUsernameScreen.tsx:102-110,445-495,509-548`. Enter a valid name and let its check settle, then shorten it to one or two letters and press Continue within the 400 ms debounce. `availabilityResults` still describes the previous name; no input identity is stored with it. `selectedDomainAvailable` stays true, and `handleContinue` sends the current invalid name without re-running the schema. The field sanitiser at 129-132 filters characters but does not enforce minimum length. **Evidence:** source trace, no network request made. **Failing test:** settle validation for `alice`, enter `a`, press Continue before advancing timers; expect no `setUsername` call. **Boundary:** changes which username requests leave the app; no local saved shape. Owner decision: validate current input at submission and derive the button gate from that same input; preserve the existing unknown-availability policy.

4. **B4 — A successful retry leaves the old Storage action error visible. `fix` (low).** `app/features/settings/screens/SettingsStorageScreen.tsx:60-70,119-155,303` and its error rendering around 463. Copy Debug Logs, Copy coco Report, Share Full Dump and Export Log File set the shared `error` on failure but never clear it on retry/success. Only inventory loading clears it (95). Thus a failed clipboard write followed by a successful copy shows “Copied” while retaining “Failed to refresh inventory: …” for the earlier copy error. **Evidence:** complete handler/state trace. **Failing test:** reject the first clipboard write, resolve the second; assert success and absence of the old inline error. **Boundary:** local display state only; no saved data or network change. **Commit:** clear the action error when retrying and use an action-neutral error label, retaining existing operation behavior.

## Inconsistent

1. **I1 — ThemeProvider's startup contract contradicts its implementation. `fix` (low).** `app/shared/providers/ThemeProvider.tsx:36-49,152-155`. The API comment says first render waits for both wallpaper and profile theme hydration; the implementation waits only for wallpaper, and the adjacent comment explains that waiting for profile hydration would deadlock. **Commit:** correct the API comment to describe the actual gate and the profile-store dependency. No behavior, storage or network change. This is a documentation correction, not a proposal to add the second gate.

2. **I2 — File-cache documentation promises preservation that the write sequence does not provide. `list` (medium).** `app/shared/lib/persist/fileCacheStorage.ts:16-20,56-61,65-80`. It says a cut-short write leaves the previous value. The writer explicitly deletes the old file before moving the temporary file. A failed move or termination between those operations leaves neither value at the readable path; the reader ignores `.tmp`. **Verified:** actual module transpiled in memory with filesystem stand-ins, old cache present, temporary write successful, move rejecting; the next read returned null while the temporary file remained. The initial probe had an incorrectly shaped AsyncStorage default-export mock; the corrected probe produced this result. This is a refetchable cache, not evidence of lost ecash. **Owner decision:** accept the cache-loss window and correct the contract, or require replacement/recovery semantics and fault-test the storage adapter. **Boundary:** any runtime repair changes saved cache handling; therefore list, even though a comment-only correction is small.

## Inefficient

1. **E1 — Balance/name updates trigger a complete storage inventory scan. `list` (low).** `app/features/settings/screens/SettingsStorageScreen.tsx:295,332-352`; `app/shared/stores/global/profileStore.ts:316-341`; `app/features/wallet/hooks/useProfileBalanceSync.ts:8-14`; `app/shared/lib/debug/storageInventory.ts:44-68,103-112,143-155`. The screen subscribes to the full profiles array and uses its identity as the load effect dependency. Both cached-balance and metadata updates map that array, so each update while the screen is mounted re-runs inventory even when the set of accounts is unchanged. **Cost established from calls:** each invocation enumerates AsyncStorage keys, lists the SQLite directory, and performs `2 + 3 × distinct account indices including 0 + imported public keys` SecureStore reads. No native duration was measured. **Owner decision:** determine whether balance/name changes should refresh inventory; if not, key automatic reloads to account identity/source and retain explicit Refresh. This is a candidate with a counted I/O cost, not a claimed measured speed-up. No saved or sent format needs changing.
